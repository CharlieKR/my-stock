# Slack 없는 My Stock 데이터 구조 설계

검토일: 2026-09-20 KST. 상태: 로컬 구현 진행 후 적용 가이드 작성. 운영 DB·매매 작업·Slack 설정은 변경하지 않았다. 실제 구현 범위·초기 스키마 단순화·운영 미적용 항목은 [적용 가이드](PROJECT_INTEGRATION_GUIDE.md)를 기준으로 확인한다.

## 1. 결정안

**신규 Supabase 프로젝트를 만들지 않고, kst와 lst의 기존 프로젝트에 조회용 데이터를 추가한다.** 각 매매 프로그램이 자신의 DB에 구조화된 주문·정산 결과를 저장하고, My Stock의 읽기 서버가 두 DB를 조회해 앱에 제공한다.

```text
kst: 주문 계획 / 실행 / 잔고 대사 / 정산 → kst Supabase의 reporting 데이터 ─┐
                                                                       ├→ My Stock 읽기 API → iOS
lst: 주문 계획 / 실행 / 잔고 대사 / 정산 → lst Supabase의 reporting 데이터 ─┘
환율 수집 작업 → lst reporting.fx_rates ───────────────────────────────────┘
```

Slack은 데이터 수집 경로에서 빠진다. 앱을 열지 않아도 기존 서버 작업이 일별 기록을 남긴다. API 조회가 매매 실행이나 잔고 대사를 유발하지 않는다. 월별 성과 계산은 API 한 곳에서 수행한다.

기존 두 DB는 원장과 정산 결과를 보관하는 원본이다. API의 로컬 캐시는 다시 만들 수 있는 사본이며, 새 중앙 DB를 전제로 하지 않는다. 같은 reporting 구조를 쓰므로 나중에 별도 프로젝트로 조회 데이터만 옮기기도 쉽다.

## 2. 실제 코드·DB 확인 결과

로컬 설정이 가리키는 서로 다른 Supabase 프로젝트 두 곳에 GET으로 스키마와 기록 범위를 조회했다. 아래 건수는 조회 시점 기준이며 실제 체결 건수와 같지 않다. 대시보드의 요금제·백업 설정·운영 서버 환경 일치 여부는 이번 검토 대상에 포함하지 않았다.

| 출처 | 확인한 데이터 | 범위·건수 | 활용과 한계 |
| --- | --- | --- | --- |
| kst | `broker_snapshots`, kind=assets | 키움 133일: 2026-03-10~09-18, LS 90일: 05-11~09-18 | 계좌별 총자산·현금·평가액·원금·일별 입출금·손익이 이미 저장됨 |
| kst | `positions_daily` | 901행, 02-13~09-18 | 보유 수량·평가액. 과거 HYXL 이전 다른 종목도 포함 |
| kst | `execution_portfolio_cashflows` | 10행, 07-06~09-07 | 외부 입출금과 계좌 간 이동을 분류해야 함 |
| kst | `hyxl_order_queue` | 251행, 06-29~09-21 | 주문 계획·제출 상태. 미래 계획도 있으므로 체결과 구분 |
| kst | `orders`, `fills`, `portfolio_runs` | 원장·실행 상태 테이블 확인 | 주문/체결 상세 및 정산 성공 여부 대조 |

따라서 **HYXL은 기존 자산 스냅샷을 재사용하기 좋고, SOXL은 최종 자산 스냅샷의 영구 저장이 우선 필요하다.** 주문 원장만으로 과거 현금·수수료·RP·외부 입출금을 완전히 재현할 수 있다고 가정하지 않는다.

### 원본 의미를 보존해야 하는 부분

- kst의 키움/LS 과거 스냅샷은 HYXL 도입 전 계좌 운용도 포함한다. 가장 오래된 3월 기록을 전부 HYXL 수익으로 이름 붙이지 않는다. HYXL 편입 시작일과 계좌 범위를 유효기간으로 관리한다. 현재 확인된 HYXL 주문 큐는 6월 29일부터다.
- HYXL은 고정 종목코드 하나가 아니다. 기존 ACE `0194T0.KS`와 이후 KODEX `0193T0.KS` 등 실제 운용 이력을 포괄한다. 원장 종목코드와 앱의 투자 그룹 HYXL을 분리한다.
- kst 원장에는 같은 날짜·금액의 키움 출금과 LS 입금이 있다. 7월 6~8일 기록은 내부 이체 후보이며, 양쪽 원장 근거를 확인해 `transfer_id`로 연결한다. 금액·날짜가 같다는 이유만으로 자동 확정하지 않는다.
- lst는 SOXL 운용 대상 외 보유 종목을 별도로 제외해 표시한다. 기존 현금의 귀속 범위도 명시하고, 계좌 전체 자산과 전략 자산을 섞지 않는다.
- lst의 main 손익은 기존 주문 재생 로직과 실제 체결 대조를 통해 계산된다. 단순 `realized_pnl` 합계나 `orders.status=success`를 체결 확정으로 치환하지 않는다.
- shadow/paper 테이블의 평가액은 실거래 자산에 넣지 않는다. 일부 shadow 설정이 실제 주문 계획에 사용되더라도, 시뮬레이션 평가액까지 실자산이 되는 것은 아니다.

## 3. DB 선택 비교

| 방식 | 장점 | 부담 | 판단 |
| --- | --- | --- | --- |
| 앱/API가 기존 매매 테이블만 직접 조합 | 초기 추가 저장이 적음 | SOXL 최종 NAV가 없고 주문·체결·현금 의미가 화면에 결합됨 | 임시 데이터 확인용 |
| **기존 두 프로젝트에 reporting 추가** | 기존 운영·백업 체계를 활용, 정산 직후 같은 DB에 저장, 별도 프로젝트 불필요 | 소스별 저장 어댑터와 권한 설정 필요 | **현재 추천** |
| 새 My Stock Supabase 프로젝트 | 조회 서비스 수명·접근권한·백업을 독립 운영 | 별도 비용/운영, 두 DB에서 복제·재시도·삭제/수정 동기화 필요 | 여러 사용자/투자처 또는 강한 운영 분리가 필요할 때 |

현재 확인한 데이터 규모와 개인용 일일 조회에는 중앙 DB를 추가할 근거가 부족하다. API나 기존 DB 하나가 일시 중단되면 해당 소스의 마지막 정상 데이터와 갱신 지연을 표시한다. 기존 매매 DB의 장애·삭제와 무관한 독립 보존이 요구되면 새 프로젝트로 전환한다. 단순 스키마 분리는 프로젝트 수준 장애 격리를 제공하지 않는다.

## 4. 저장 구조

두 프로젝트에 Data API에 노출하지 않는 `reporting` 스키마를 둔다. 원본 매매 테이블은 유지하고 조회에 필요한 결과만 정규화한다. 아래는 제안이며 아직 생성하지 않았다.

| 테이블 | 핵심 필드 / 키 | 용도 |
| --- | --- | --- |
| `portfolio_memberships` | investment_id, portfolio_id, strategy_id, effective_from/to, instrument_set, currency, valuation_policy_version | SOXL/HYXL·계좌·전략의 역사적 범위와 중복 합산 방지 |
| `daily_snapshots` | snapshot_id, portfolio_id, valuation_date, valued_at, market_timezone, revision, nav, cash, position_value, principal, pnl_breakdown, quality, source_refs, calculation_version | 날짜별 총자산과 구성. `(portfolio_id, valuation_date, revision)` 유일 |
| `daily_details` | snapshot_id 또는 batch_id, detail_type, source_id, payload_version, payload | 계획 주문, 실제 체결, 포지션, RP/CMA, 정산 요약. 숫자를 담은 구조화 JSON 사용 |
| `cash_events` | source_event_id, portfolio_id, occurred_at, effective_date, kind, amount, currency, transfer_id, revision, source_ref | 외부입출금·내부이동·수익·비용·정정 구분. 소스 식별자로 중복 방지 |
| `publication_batches` | batch_id, portfolio_id, business_date, stage, status, revision, source_watermark, completed_at, error_code | 주문 계획/실행/정산의 완결성, 갱신 상태 및 재처리 기준 |
| `fx_rates` — lst에만 | base, quote, rate_date, published_at, rate, provider, revision | USD/KRW 환율의 지속 저장. 다른 통화 확장 가능 |

금액·수량은 적절한 정밀도의 PostgreSQL `numeric`으로 저장하고 API에서는 십진 문자열로 전달한다. Swift는 `Decimal`로 금액을 취급하고 차트 좌표/최종 표시 단계에서만 변환한다. 0과 미수집/null을 구분한다.

스냅샷 품질은 `broker_reconciled`, `reconstructed`, `legacy_archive`, `incomplete`로 구분한다. 최신성은 별도 필드로 표현한다. 정산 fallback이나 현금 조회 실패는 `broker_reconciled`로 올리지 않는다. 전략별 손익이 계좌 총손익에 맞춰 배분된 경우 `allocation_method`를 남겨 직접 관측값과 구분한다.

계좌와 하위 전략 스냅샷을 모두 보관해도 합산에는 정해진 최상위 구성원만 사용한다. 앱의 총자산은 동일 자금을 두 번 더하지 않는다. 주문가능금액을 순현금으로 간주하지 않고, RP 평가액·미결제 대금의 포함 관계를 정책으로 기록한다.

## 5. 수집과 발행

### kst

1. HYXL 주문 계획 저장 후 계획 배치를 발행한다. 아직 제출하지 않은 계획도 앱에서 확인할 수 있게 한다.
2. 주문 제출/체결 상태 변경은 원장 ID와 증권사 체결 ID를 유지해 반영한다.
3. `rebalanceSettle.ts`의 잔고 대사와 성과 계산 이후 기존 `broker_snapshots`·`positions_daily`·입출금·CMA 결과를 reporting으로 저장한다.
4. 필수 스냅샷 저장 실패를 정상 정산처럼 노출하지 않는다. `portfolio_runs`와 발행 배치를 함께 확인한다.

### lst

1. `preValidateOrders.ts`에서 만들어지는 계획 결과를 별도 계획 배치로 저장한다. Slack 텍스트만 있는 사전 주문표를 놓치지 않는다.
2. `executeOrders.ts` 및 tail 작업에서 주문/체결 결과를 원장과 연결한다. 제출 성공·부분체결·전량체결·취소·실패·스킵을 구별하고 체결량/평균가/수수료/대사 시각을 보존한다.
3. `dailyReport.ts`의 잔고 대사, 누락 주문 보정, LOC 정산, RP 수익 반영, 종가 저장을 유지한다.
4. 자산 계산을 `buildDailySnapshot()`으로 분리해 숫자·구성 내역·품질 상태를 반환하게 한다. Slack 서식의 `cashLabel`을 다시 숫자로 파싱하지 않는다.
5. 총자산뿐 아니라 계산에 사용한 실잔고/현금/RP·실체결 매핑을 함께 저장한다. 현재 summary에 없는 원시 숫자와 fallback 여부를 명시적으로 추가한다.

**Slack 중단은 전송 계층만 끄는 변경이다.** lst의 `dailyReport` cron 자체를 제거하면 정산·대사도 중단될 수 있다. 현재 `DAILY_REPORT_FULL_SLACK=false`는 전체 Slack 중단 스위치가 아니다. 전송 어댑터에 명시적인 on/off를 추가하고 스레드 생성 성공 여부가 DB 저장이나 매매 진행 조건이 되지 않게 한다. 전환 후 시작 시점의 Slack 환경변수 필수 검사도 제거한다.

각 소스 안에서는 일별 snapshot/details/batch 완료 처리를 한 트랜잭션으로 발행한다. 원래의 매매 트랜잭션에 조회용 작업을 결합하지 않는다. 발행 재시도는 이미 저장된 정산 결과를 사용하며 주문 실행을 재호출하지 않는다. 원본 저장 후 발행 실패는 성공 원장/정산과 완료 배치를 대조해 복구한다. 기존에 보존하지 않던 lst 증권사 조회 결과는 먼저 영구 보존해야 이 재시도가 가능하다. DB 자체가 내려간 경우에는 민감정보를 보호한 서버 로컬 재시도 파일과 실패 상태를 사용하고, 이후 날짜의 실잔고를 과거 날짜 잔고로 쓰지 않는다.

동일 입력의 재실행은 내용 해시로 멱등 처리하고, 변경된 입력만 revision을 올린다. 수정/삭제는 취소·정정 이벤트와 변경 커서에 남겨 과거 월도 다시 계산한다. 수정 시각이 없는 기존 lst 원장에는 추가 변경 추적 또는 범위 재대조가 필요하다. 거래일 최근 7일 조회만으로 모든 과거 정정을 잡았다고 간주하지 않는다.

## 6. 월별 수익과 전체 원화 자산

수익 계산의 기준은 정산 자산과 **실제 현금흐름 원장**이다. 현재 앱의 `(자산 - 누적손익)` 차이로 입출금을 추측하는 방식을 교체한다.

```text
월 자산 변화 = 월말 NAV - 전월말 NAV
월 수익금액 = 월 자산 변화 - 해당 조회 범위의 순외부유입
전체 원화 NAV = HYXL NAV(KRW) + SOXL NAV(USD) × 해당 시점 USD/KRW
```

- SOXL 단독은 USD, HYXL은 KRW, 전체는 KRW가 기본이다. 실현손익·미실현손익·이자·수수료의 구성과 평가손익을 포함한 총수익을 구별한다.
- 계좌별 화면에서는 다른 계좌로 보낸 돈도 해당 계좌의 유출이다. 두 계좌를 합친 HYXL에서는 연결된 내부 이체 양쪽을 상계한다. SOXL과 HYXL 사이의 이체도 전체 범위에서는 내부 이동이다.
- 이체가 날짜를 넘기면 이동 중 자금을 별도 자산으로 인식해 일시적인 자산 급락을 만들지 않는다. 환전 이체는 양 통화 원금·실제 체결환율·수수료를 연결한다.
- RP/CMA 이자는 수익이고 원금 입금이 아니다. RP 매수/환매 원금은 자산 형태 변경이며 외부입출금이 아니다. 이미 NAV에 포함된 이자를 총수익에 다시 더하지 않는다.
- 전체의 외부입출금은 이벤트 시점 환율로 환산한다. 월말 환율 하나를 모든 입출금에 적용하지 않는다. 전체 원화 수익에는 환율 변동 효과가 포함된다고 표시한다.
- 현금흐름이 없는 기간은 시작 NAV 대비 수익률을 사용한다. 현금흐름이 있고 유입 전후 평가가 없으면 날짜 가중 Modified Dietz `(기말-기초-ΣCF)/(기초+Σw·CF)`를 사용하고 추정으로 표시한다. 분모가 0 이하이거나 원장/기준 자산이 불충분하면 수익률은 미제공한다. 정확한 TWR은 현금흐름 직전·직후 평가가 충분할 때 후속 도입한다.
- 첫 기록월은 확보된 기준일부터 부분 기간으로 표시한다. 전월말 또는 시작 기준 자산이 없으면 완전한 월 수익으로 제시하지 않는다. 기록 없는 월의 자산을 0원으로 채우지 않는다.

SOXL은 미국 거래일과 실제 UTC 평가 시각을 함께 저장하고, HYXL도 한국 거래일과 실제 시각을 저장한다. 종합은 각 한국 날짜의 23:59 KST까지 이용 가능한 최신 확정 스냅샷과 환율로 평가한다. 따라서 한국 아침에는 미국 전일 종가와 한국 전일 종가, 한국 정산 이후에는 미국 전일/한국 당일 값이 함께 보일 수 있다. 각 구성원의 기준일을 표시하고 서로 다른 종가를 동시 평가처럼 표현하지 않는다. API는 장래 시각의 데이터나 환율을 소급 사용하지 않는다.

시장별 휴장 캘린더로 예정된 이월과 갱신 실패를 구분한다. 기대한 다음 정산이 누락되면 마지막 자산은 보여 주되 최신 확정값으로 표시하지 않는다. 장기 휴장/소스 누락의 상한을 별도 정책으로 관리한다. 진행 중인 월은 마지막 공통 평가 시점까지의 잠정값이다.

기존 환율 공급자를 유지하되 API 요청 때마다 과거 전체를 다운로드하지 않고 일별 작업이 DB에 저장한다. 공급자·환율 기준일·발표시각·정정 이력을 함께 보관하고 캐시/재시도한다. 공급자 응답에 발표시각이 없으면 실제 수집시각을 보수적 이용 가능 시각으로 사용한다. 과거 복원 환율은 해당 한계를 표시한다.

## 7. API와 앱

기존 Node 읽기 서버를 확장한다. 실제 기기 사용에는 항상 실행되는 서버와 HTTPS 주소가 필요하다. 현재 로컬 Mac 서버만으로는 Mac이 꺼진 동안 새 데이터를 읽을 수 없다. 기존 운영 서버의 여유 자원을 확인한 뒤 별도 서비스 프로세스로 배치하는 것을 우선안으로 한다.

| API 제안 | 응답 |
| --- | --- |
| `GET /v2/overview` | 소스별 최신 확정값, 갱신 상태, 실제 조회 가능한 시작/종료일 |
| `GET /v2/daily?investment=SOXL&cursor=...` | 날짜별 요약, 계획/진행/정산 상태, 페이지 커서 |
| `GET /v2/daily/SOXL/2026-09-18` | 자산 구성, 전략별 주문 계획/실행/체결, RP/CMA, 정산 근거 |
| `GET /v2/performance?scope=all&from=...&to=...` | 월별 수익·수익률·순입출금·자산 변화, 일별 자산, 계산 방식/품질 |
| `GET /v2/health` | 소스별 마지막 성공/예정 정산·지연, 민감정보 없는 오류 상태 |

응답에는 `schemaVersion`, `calculationVersion`, `generatedAt`, `sourceAsOf`, `quality`, `revision`을 넣는다. 두 DB의 읽기는 분산 트랜잭션으로 가장하지 않고 소스별 revision 조합을 응답/캐시 키로 남긴다. 한 소스 실패 시 투자별 화면은 정상 제공하고, 종합은 이월 여부 또는 계산 불가를 설명한다.

SOXL/HYXL 탭의 Daily 카드와 My의 종합 리포트 구조는 유지한다. Slack 스레드/원문 버튼은 구조화된 주문 상세·정산 내역으로 교체한다. 로그인 화면은 추가하지 않고 기존 기기 연결 키를 Keychain에 저장하는 흐름을 유지한다. 새 데이터가 없어도 마지막 동기화 내역은 오프라인에서 볼 수 있다.

### 종합 리포트 계산 결과와 앱 디스크 캐시

2026-09-20 사용자 의견 반영: **종합·월별 계산 결과를 별도 DB 테이블로 영구 저장하지 않는다.** DB에는 재계산 가능한 원본인 일별 자산·현금흐름·환율·정정 이력을 보관한다. 서버가 조회 범위에 맞는 결과를 계산하고, 앱은 그 응답을 디스크에 저장한다. 앱 자체에서 동일 성과 공식을 다시 구현하지 않는다.

1. 종합 리포트 진입 시 저장된 결과를 즉시 표시한다. 앱을 종료했다 켜거나 네트워크가 없어도 마지막 조회 결과를 볼 수 있다.
2. 앱 활성화·리포트 진입 시 갱신 확인을 하되, 짧은 간격의 중복 요청은 합친다. 사용자의 새로고침은 즉시 확인한다. 서버는 원본 revision과 계산 버전을 확인하고 변경이 없으면 `ETag`/`If-None-Match`의 `304`로 응답해 전체 결과 전송과 재계산을 생략한다.
3. 변경이 있으면 서버가 결과를 계산해 반환하고 앱은 유효성을 확인한 뒤 디스크 파일을 원자적으로 교체한다. 화면에서도 새 결과로 갱신한다. 서버의 결과 캐시는 선택적인 속도 개선이며, 재시작 후 원본 DB로 복구할 수 있어야 한다.
4. 월말이 지난 결과도 원장·입출금·환율 정정 또는 계산 버전 변경 시 갱신한다. 단순히 지난달이라는 이유로 영구 고정하지 않는다. 초기에는 해당 조회 범위 전체를 무효화하는 보수적인 방식을 사용한다.
5. 통신 실패는 마지막 정상 캐시를 보존하고 기준 시각과 갱신 지연을 표시한다. 원본 revision뿐 아니라 진행 중인 기간의 종료일·평가 기준시점이 바뀐 것도 갱신에 반영한다. health 최신성은 리포트 내용과 별도로 확인한다.

캐시 식별자는 `서버/데이터셋 ID + 투자 범위 + 기간 + 기준 통화 + schemaVersion`이다. 파일에는 결과와 함께 원본별 revision, 환율 revision, `calculationVersion`, ETag, 평가 기준시각, 저장/마지막 확인 시각을 보관한다. 서버나 데이터셋을 바꾸면 이전 연결 캐시를 섞어 표시하지 않는다. 연결 키 자체는 파일명/캐시에 넣지 않는다.

개인용 데이터 규모에서는 기존 `ReportStore`처럼 Application Support의 JSON 파일과 원자적 쓰기로 시작한다. 일별/상세/종합 캐시는 구분하고, 재생성 가능한 파일은 기기 백업에서 제외한다. 앱 삭제·캐시 삭제 후에는 API에서 다시 받는다. 별도의 앱 내 DB는 조회량이 커져 부분 검색·갱신이 필요할 때 검토한다.

v2 구현에서는 서버에서 계산한 세 투자 범위의 성과·일별 기록·상세를 같은 응답으로 받아 `report-cache.json`에 원자적으로 저장한다. 별도 월별 파일 대신 전체 응답을 한 revision으로 보관해 부분 갱신 불일치를 피한다. 샘플 모드만 기존 앱 내 계산을 사용한다.

읽기 API에는 DB별 reporting 테이블에만 SELECT 가능한 전용 Postgres 역할을 사용한다. RLS를 켠 경우 해당 역할의 조회 정책도 명시한다. 함수 실행·원장 쓰기·스키마 생성 권한은 주지 않는다. 소스 작업의 발행 역할과 환율 수집 역할도 별도로 최소 권한을 부여한다. 서버 배치 방식에 맞는 직접 연결 또는 풀러를 선택한다. [Supabase 연결 문서](https://supabase.com/docs/guides/database/connecting-to-postgres)

iOS에는 Supabase service-role/secret 키나 증권사 키를 넣지 않는다. 로그인 화면이 없어도 데이터가 공개되는 구조가 되어서는 안 된다. HTTPS+기기별 읽기 키, 폐기/재발급, 접근 제한을 적용한다. service-role/secret 키는 RLS를 우회하므로 서버에서만 사용해야 한다. 기존 프로젝트의 Data API 전체를 비활성화하면 매매 프로그램에 영향을 줄 수 있으므로, 새 스키마의 노출/권한만 제한한다. [Supabase 보안 문서](https://supabase.com/docs/guides/database/secure-data)

## 8. 과거 데이터 전환

1. 기존 `.local/reports.json`을 해시와 함께 변경 불가한 과거 자료로 보관한다. 여기서 가져온 값에는 `legacy_archive` 출처를 붙인다. 추가 Slack 조회나 Slack 토큰이 없어도 이 파일은 읽을 수 있다. 현재 캐시에 없는 전체 스레드 상세까지 보존되었다고 가정하지 않는다.
2. kst의 자산 스냅샷·입출금·포지션을 전체 기간 조회해 복원하되, HYXL 편입 범위를 적용한다. 이전 계좌 운용 내역은 별도 과거 계좌 기록으로 구분한다.
3. lst는 3월 25일 이후 주문·종가·입출금·RP 기록과 확보된 기준 자산을 대조한다. 증권사 과거 잔고/거래내역이 확보되는 범위는 보강하고, 불완전한 계산값은 `reconstructed`로 저장한다. 시세가 2025년부터 있다고 2025년 자산 곡선을 생성하지 않는다.
4. 기존 Slack 유래 일별 자산과 DB 복원값을 비교해 차이 목록을 남긴다. 반올림 차이·원금 보정·이체·정산시점 차이를 구분한다. 다른 값을 무조건 최신 값으로 덮어쓰지 않는다.
5. 전환일 이후에는 새 구조화 스냅샷을 원본으로 삼는다. 과거 미확정 구간은 자산 기록을 보여 주되 수익금/수익률의 한계를 개별 표시한다.

과거 기록을 더 오래 보여 주는 것과 그 전체 기간의 정확한 수익률을 계산하는 것은 별도 문제다. 확인된 범위에서 최대한 보존하고, 없는 기준 자산·현금흐름을 만들어 채우지 않는다.

## 9. 구현 순서와 완료 기준

1. **저장 기반:** reporting 마이그레이션, 권한, 날짜/금액/품질 계약 및 조회 범위 매핑을 작성한다. 운영 환경 일치·백업/복구 상태를 확인한다.
2. **소스 발행:** kst 기존 정산 결과 어댑터, lst 최종 자산/체결 근거 영구 저장, 양쪽 계획/실행 발행을 붙인다. DB 전송 실패 재시도는 매매와 독립시킨다.
3. **과거 이관:** 기존 파일 보존, 읽기 전용 백필, 기준 자산/이체 대조, 출처별 차이 보고서를 만든다. 실거래 job을 백필 도구로 실행하지 않는다.
4. **읽기 API/앱:** v2 조회·월별 계산·환율 수집을 붙이고 앱의 Slack 상세를 구조화 화면으로 교체한다. 기존 v1은 전환 중 호환 어댑터로만 유지한다.
5. **Slack 종료:** 양쪽 시장 정산과 주문 계획이 DB→앱으로 전달되는 것을 확인한 뒤 전송을 끈다. Slack 변수 없이 시작/실행/정산이 되는지 검증하고, 다른 알림 사용처가 없는 토큰만 제거한다. 이후 v1 Slack 수집 경로를 폐기한다.

핵심 완료 기준:

- Slack 토큰이 없는 환경에서도 주문 계획, 실행 상태, 두 시장의 일별 자산이 정상 갱신된다.
- 소스 구조화 값과 reporting의 자산이 같은 반올림 기준에서 일치한다. SOXL의 fallback 잔고는 확정값이 되지 않는다.
- 내부 이체·외부 입출금·RP 이자·부분체결·정산 수정·첫 기록월·월말 휴장·미국 DST·서로 다른 시장일을 검증한다.
- 원장/발행 재실행이 주문 재실행·중복 체결·중복 입출금을 만들지 않는다. 오래된 월의 정정도 다음 조회에 반영된다.
- DB 한쪽 중단 및 환율 지연 시 마지막 정상 데이터와 정확한 기준일을 표시한다. 누락을 0원으로 계산하지 않는다.
- iOS/API 읽기 자격증명으로 매매 원장에 쓰기나 주문 실행이 불가능하다.
- 보고서 DB 백업 및 복구 후 API 캐시를 지우고도 전체 기록을 다시 조회할 수 있다.
